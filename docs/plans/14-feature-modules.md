## 1. 接手本仓库先读这里

项目目标是科研伙伴：发现 → 理解 → 关联 → 探索 → 验证 → 产出 → 持续积累。
最终产物包括文献清单、阅读笔记、知识图谱、研究问题、证据矩阵、实验方案、论文草稿与可追溯探索历史。

任何开发 agent 开工前依次阅读：AGENTS → 本文 → progress.json → 架构现状/问题台账 → 对应契约与实现。
先选择本计划中的任务包，再确认正式任务卡、依赖、设计批准、数据归属和验收环境；不能仅凭模块名称启动开发。

- M1–M24 是功能分类，不是新目录、新服务或第三套进度。保留 M1–M17，补充 M18–M24。
- P0–P3 是既有工程阶段；V1–V4 是产品价值版本。后续规划波次不自动变成正式 P4/P5，也不计入完成度分母。
- 当前实现不能从页面、旧计划或本表推定。已有恢复、权限和依赖整改复用，不重做；并不据此宣布整个模块完成。
- Go 唯一公开入口和全局调度；Python 执行局部任务；PG 是业务真相，Milvus 是可重建索引。
- 用户确认的是完整模块范围与编排工作；[P1 设计审查](../../contracts/p1-design-review.md)仍须逐项确认，不能自动改为 approved。
- 同一模块跨阶段交付，每次交付应有能演示的纵向链路，不能先写完所有后端或页面再集中拼装。

## 6. 后续 agent 的执行与交接协议

1. 读取上述权威入口，运行 Git 状态检查，核实任务相关实现与现有能力；保留他人改动。
2. 认领一个任务包中的一个具体增量。列出输入、输出、正式任务依赖、真实验收命令/期望、证据级别、风险和非目标。
3. 核实阶段、数据与接口设计门禁；模块范围已确认不等于所有新 schema/接口/工具权限已批准。
4. 对共享契约/迁移/sqlc/锁文件/progress.json 指定一个集成负责人。没有分工授权时不擅自派生 agent；并行开发不得同改共享入口。
5. 先冻结需协作的接口，再允许同阶段不冲突的 UI/后端/测试分工；每个增量仍交付完整可验证行为，不提前解锁跨阶段实现。
6. 验证必须区分 none/mock/real/e2e；记录实际收集/通过/跳过、环境、样本与限制。禁止用新建空库证明历史存量兼容。
7. 失败与未完成项写明，不改弱断言；更新契约、现状、问题台账、正式任务状态和本轮 WORKLOG，再生成进度页。
8. 按关注点提交，清理本轮进程/隔离对象、保留原文/卷/备份；发布按用户授权执行。
