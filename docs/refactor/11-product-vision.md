# 11 — 产品愿景：从可信论文 RAG 到 Research OS

> **本文状态（2026-10-11）**：性质=**愿景 / 产品决策**。上游是项目负责人 2026-10-11 给出的产品规划。
> 与工程架构轴的关系见 §7：**本文不改变 `P0–P3` 的阶段顺序**，它描述的是"产品价值轴"。
> ⚠️ **本文 §4 的十项能力绝大部分尚未进入 [`progress.json`](../progress.json)**——缺口清单见 §8，登记与否待拍。

## 0. 一句话

ResearchPilot 不是一个聊天机器人，而是一个**科研伙伴**：输入研究方向，建立一个能够持续积累知识、追踪证据、执行研究任务的科研工作空间。

> 它不仅回答论文里的问题，还能够：理解你正在研究什么、知道你读过什么、主动发现你不知道什么、
> 寻找支持或反驳的证据，并帮助你决定下一步应该研究什么。

## 1. 定位与交付物

**ResearchPilot — Your AI Research Partner**：从论文阅读 → 科研探索 → 研究成果。
主链路：**发现 → 理解 → 关联 → 探索 → 验证 → 产出**。

最终科研交付物：文献清单、阅读笔记、知识图谱、研究问题、证据矩阵、实验方案、论文初稿，
以及**完整可追溯的科研探索历史**。

## 2. 三层能力（长期演进骨架）

| 层 | 承担什么 |
| --- | --- |
| Research Assistant | 回答问题 · 阅读论文 · 整理知识 |
| Research Agent | 制定计划 · 执行任务 · 验证证据 · 生成报告 |
| Research Partner | 积累长期记忆 · 发现研究缺口 · 质疑结论 · 建议下一步 |

最深的价值不是"记住用户聊过什么"，而是**记住这个科研项目建立了哪些知识、验证了哪些结论、还有哪些问题没有解决**。
这一点直接决定架构要求：项目状态必须是可持久、可查询、可审计的（对应架构律 **L3** PG 唯一真相），
模型输出必须被证据绑定后才算事实（**L4**）。

## 3. 五个产品入口

| 产品模式 | 用户想做什么 | 系统承担什么 |
| --- | --- | --- |
| Ask Papers | 问一个具体问题 | 可信、可引用的论文 RAG |
| Deep Reading | 精读一篇论文 | 分层解析、讲解、提问、笔记 |
| Research Mission | 探索一个科研课题 | 多 Agent 自主检索、分析、再规划 |
| Research Lab | 验证一个研究想法 | 假设管理、实验规划、代码与结果分析 |
| Research Writing | 完成科研成果整理 | 综述、技术报告、LaTeX 草稿、参考文献 |

五种能力既能独立使用，也围绕**同一个科研项目共享文献、证据与进度**。

## 4. 十项核心能力

1. **AI 论文图书馆**：PDF / DOI / arXiv / 研究方向导入；元数据识别、去重、结构化解析、向量索引、引用关系、主题分类；
   论文语义书架（自动成"共识安全证明""同步模型""UC 理想功能"等主题群）；预印本/会议版/期刊版关系；Zotero / BibTeX 对接。
   要能回答"**这篇论文为什么在我的知识库里**"。
2. **Deep Reader**：左 PDF 右助手 + 论文结构、公式、定理、引用、笔记。论文结构导航、公式解释（符号/条件/推导关系）、
   定理解析（前提/结论/证明步骤/依赖引理）、**每次回答可跳转到 PDF 位置**、难度分级讲解、一键存笔记、论文结构图。
   并为形式化安全研究提供 **Formal Methods Reading Mode**（Network Model / Adversary Model / Timing Assumptions /
   Safety / Liveness / Ideal Functionality / Simulator / 证明依赖）。
3. **Multi-Paper Analysis**：输入"比较这 8 篇论文对部分同步网络的建模方式"，产出**比较矩阵**（系统模型/时间假设/安全目标/
   证明方法/局限性 × 每篇论文，每格带原文证据），而不是拼接摘要。另有 **Paper Diff**：同篇不同版本、或两篇相关论文之间的
   方法变化、假设放宽、定理增强、证明条件变化。
4. **Research Mission**（旗舰）：围绕研究目标**持续执行**，而非答一轮问题。Planner（目标分解/证据需求/阅读计划/预算）→
   Discovery → Reader → Analyst → Verifier → **Research Frontier**（发现缺口 → 创建新任务 → 补充检索与分析），
   有界自主探索直到目标满足或预算耗尽。三档模式：快速探索 / 标准探索 / 深度探索。
5. **Research Knowledge Graph**：两张图——**Knowledge Graph**（Paper/Method/Assumption/Theorem/Claim/Evidence，跨项目复用）
   与 **Exploration Graph**（Goal/Intent/Task/Finding/Gap/Hypothesis，解释"为什么走到这个结论"）。
   目标能力：点击报告里的"这一结论依赖部分同步假设"→ 反向展开相关定理、支撑段落、所属论文、以及**是哪次 Agent 任务提取的**。
6. **Research Gap Explorer**：不是泛泛列"未来方向"，而是基于论文与证据关系找缺口。每个候选问题给出：
   已有研究（类似假设的论文与定理）、模型差异（假设边界对比）、待确认之处（未检索到充分证据）、验证路径（阅读/建模/实验建议）。
   配套 **Research Hypothesis Board**：有潜力 / 需补证据 / 已被研究 / 准备验证 / 不再研究。
   **产品口径纪律：系统生成的是候选研究问题，不声称发现了全新学术贡献。**
7. **Research Lab**：从阅读走向实验与形式化验证。ML（复现计划）、分布式系统（网络假设/故障模型/协议状态机）、
   形式化验证（TLA+ / CSP# 建模草案 + 调用验证工具）、安全协议（敌手能力/安全定义/证明义务）、算法（复杂度/测试样例/实现比较）。
   目标是串起：**论文定理 → 建模假设 → 形式化规格草案 → 模型检查任务 → 检查结果 → 研究笔记**。
   口径纪律：**模型检查通过特定配置或有限状态范围，不等于一般情形下的数学证明。**
8. **Research Writing**：阅读报告、Related Work、技术综述、方法比较、研究计划、开题材料、汇报提纲、Markdown / LaTeX / BibTeX；
   结构与写作逻辑检查；**引用是否支持正文陈述**的检查。核心差异是 **Evidence-grounded Writing**：每个关键陈述关联已核验文献，
   没有来源的内容必须显式标为解释 / 观点 / 待验证。
9. **Research Radar**：把 Research Mission 存成长期项目，定期检查文献变化（新论文、技术报告、重要修订）并关联已有研究问题。
   更进一步是 **Knowledge Diff**：不是"出现了一篇新论文"，而是"新论文在哪个问题上补充、修改或挑战了你知识库里的结论"。
10. **Research Workspace**：打开的不是聊天窗口，而是科研工作区：论文知识库、科研任务、知识与探索图、研究笔记、假设与实验、
    研究报告、最近研究活动；并支持项目目标、任务清单、阅读进度、笔记、报告版本、AI 预算，后期再谈团队协作。

## 5. 三个"惊艳功能"

| 功能 | 形态 |
| --- | --- |
| ① **研究问题反向导航** | 从"我关心的问题"出发，构建 `研究问题 → 相关安全定义 → 已有模型 → 关键论文 → 理论假设 → 证明依赖 → 未解决问题` 的知识导航链，每个节点标出证据来源与不确定性 |
| ② **AI 学术质疑者（Research Critic）** | 主动检查：想法是否与已有工作重复、是否忽略必要假设、结论是否超出论文证明范围、两篇论文的"冲突"是否只是系统模型不同、创新点是否缺少相关工作支撑。不替代同行评审，但能在投稿/写报告前发现问题 |
| ③ **从科研问题生成可执行研究路线** | 不只推荐论文，还给出：需掌握的前置理论、优先阅读的论文与理由、需建立的模型/实验、可尝试的验证工具、仍缺证据的关键假设、不同路线的难度/成本/风险。任务是动态路线图，会随进展更新，而不是每次生成孤立计划 |

## 6. 差异化能力与目标用户

| 差异化能力 | 用户得到的价值 | 技术核心 |
| --- | --- | --- |
| 结构感知科研阅读 | 不只搜相似段落，而是理解论文结构 | 定理/证明/章节级解析 |
| 可信证据链 | 每个结论都有来源、可复核 | Claim–Evidence–PDF 定位 |
| 跨论文知识记忆 | 不必每次重新梳理已有研究 | Knowledge Graph |
| 主动研究探索 | 系统能发现"下一步该查什么" | Planner + Frontier |
| 长期项目记忆 | 研究任务跨天、跨会话持续推进 | Go Research Engine |
| 研究工具衔接 | 从阅读迈向实验设计与验证 | 工具化 Agent / Sandbox |

其中最有竞争力的是**证据驱动的自主探索**：系统不是为完成固定任务而盲目多搜，
而是依据未解决问题、证据缺口与研究预算，决定**是否继续、探索哪里、何时结束**。

| 用户类型 | 核心需求 | 对应能力 |
| --- | --- | --- |
| 硕博研究生 | 读论文、查资料、整理 Related Work | 文献管理、精读、跨论文分析 |
| 导师与课题组 | 项目知识积累、分工、材料审核 | 团队空间、共享知识图谱、权限 |
| 企业研究员 | 快速技术调研、方案评估、竞品分析 | Research Mission、证据报告 |
| AI/算法工程师 | 找方法、复现实验 | Paper Reader、Research Lab |
| 研究机构 | 私有数据安全、长期知识管理 | 私有部署、审计、访问控制 |

**先聚焦计算机科学方向的研究生与研究人员**：领域熟悉、可自造高质量测试任务、反馈真实。
商业化路径（个人工作台 → 课题组协作 → 机构私有部署）后期再谈，早期不做计费。

## 7. 与工程架构轴（P0–P3）的关系

**这是两条独立的轴**，不要混用编号：

| 轴 | 载体 | 性质 |
| --- | --- | --- |
| 工程架构轴 | `docs/refactor/` 的 **P0–P3**（P4 为双图/Evidence 展望） | 先立骨架、契约与数据真相 |
| 产品价值轴 | 本文的 **V1.0–V4.0**（§10） | 用户能拿到什么 |

映射关系：

| 产品版本 | 架构轴上由谁覆盖 | 差距 |
| --- | --- | --- |
| V1.0 可信学术 RAG | P0 + **P2 的数据可信化**（P2-1 chunk 真相层、P2-2 公式索引、P2-3 链路测试） | ⚠️ **顺序冲突**：V1 要求"先可信化"，架构轴把它排在 P2（Go 迁移之后） |
| V2.0 一键科研 MVP | P1（Go 接管接口）+ P3（Run/Frontier/Worker + Planner/Discovery/Reader/Analyst/Verifier/Writer + PARTIAL 报告 + 崩溃恢复） | 基本对得上 |
| V3.0 自主科研探索 | P3 后半 + P4 展望（双图、Evidence Registry） | Gap Explorer / Hypothesis Board / Research Radar / Knowledge Diff **架构轴完全没有** |
| V4.0 Research OS | 架构轴 `not_doing` 之外 | 形式化验证、实验复现、写作、协作、私有部署均未入计划 |

**顺序冲突的最小解法（建议）**：先做 **P0-2 真库基线 + chunk 正文进 PG**（两步都不需要 Go），
把 V1 的"可信化"提前，其余仍按架构轴走。

## 9. 技术借鉴：ARTEX（只借架构，不借业务）

参考项目 <https://github.com/Hinln/ARTEX>（AI 渗透测试方向）。**只参考其技术架构**：
它是 Go 单体 + 内部包分层，把很多东西做成了**一等包**——这正是 ResearchPilot 应学的组织习惯。

| ARTEX 的包 | 职责 | 对 ResearchPilot 的启示 |
| --- | --- | --- |
| `agent/` | Agent 编排 | ≈ `internal/scheduler` + `internal/worker`（已在 02 设计） |
| **`evidence/`** | 证据管理 | **Evidence Registry 应独立成包**（L4 的落地形态），而不是放到"展望" |
| **`report/`** | 报告生成 | 独立报告模块，同时承载 V2 报告与 V4 的 Research Writing |
| `llmpool/` + `llmrec/` | 模型池 + 调用/用量记录 | ≈ `model_usage_records` + 预算（P2-6）；**模型池 + 逐次记账**值得直接照搬 |
| `guard/` | 护栏 | 对应审计 §6 的 prompt injection / 工具白名单缺口 |
| **`mcphttp/` + `skills/`** | 工具与技能扩展（MCP） | Research Lab 的验证工具、学术 API 适配（OpenAlex/S2/arXiv/Crossref）都该走这一层；**现有架构文档里完全没有** |
| `notify/`、`selfupdate/`、`install.sh`/`update.sh`、`CHANGELOG.md` | 自托管产品化 | V4 私有部署/机构版需要；现在一点没有 |
| `docker-compose.bench.yml` | 独立基准环境 | 对应 P2-4 的 10–15 题回归集，值得单独一套 compose |
| `db/`、`config/`、`server/`、`web/` | 基础分层 | 与现有 `internal/db`、`internal/config`、`internal/httpapi`、`frontend/` 同构，无需变 |

## 10. 版本路线（产品价值轴）

| 版本 | 主题 | 交付 | 目标 |
| --- | --- | --- | --- |
| **V1.0** | 可信学术 RAG | PDF 可靠解析、公式/定理检索、文献管理、混合检索、原文定位、结构化阅读卡片 | 比普通聊天式论文问答**更可靠** |
| **V2.0** | 一键科研 MVP | Go Research Engine、Python Agent、学术搜索、Planner、Reader、Analyst、报告生成、执行恢复 | 从问题到一份**可信的多文献研究报告** |
| **V3.0** | 自主科研探索 | 知识图谱、探索图、动态 Frontier、Evidence Verifier、Gap Explorer、长期 Research Radar | 不只回答问题，还能**主动扩展研究边界** |
| **V4.0** | Research OS | 科研工具集成、形式化验证辅助、实验复现、科研写作、团队协作、机构私有部署 | 覆盖从知识获取到成果管理的主要流程 |

前提：**V1.0 必须先完成现有基础的修复与可信化**，否则高级功能只会放大原有问题。

## 11. 非目标（明确不做）

- 不承诺"输入主题一键生成一篇论文"；终局是"输入研究方向，建立一个持续积累的科研工作空间"。
- 不把模型输出当作可信事实（L4）；报告中的推断必须与证据区分。
- 不把"模型检查通过"表述为"一般情形已证明"。
- 不把 Gap Explorer 的候选问题宣传为"全新学术贡献"。
- 沿用 `02-target-architecture.md` §9：不引入 Kafka / RabbitMQ / Neo4j / 服务注册中心；不建两个全局调度器。
- 早期不做计费系统；团队协作与机构私有部署留到 V4。
